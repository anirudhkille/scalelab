# Decisions

One line each: decision, and why.

- **bun instead of pnpm** — the plan says pnpm, but the user chose bun and pnpm is not installed in this environment.
- **Node 26** — user requirement; `engines.node` is `>=26`.
- **oxlint instead of ESLint** — user requirement. oxlint cannot express `consistent-type-definitions` or feature import boundaries, so `scripts/check-conventions.mjs` enforces those rules alongside oxlint.
- **Vitest instead of an unspecified test runner** — user requirement; jsdom + Testing Library are configured.
- **React Router v8** — the plan allows React Router or TanStack; React Router is already installed and wired.
- **shadcn Base UI, preset `nova` / style `base-nova`** — matches the plan's Base UI requirement.
- **No `number-field` component** — it is not in the Base UI registry (CLI returned 404); the plan's fallback is `Input` plus a custom stepper when parameter forms arrive in M3.
- **Inter + JetBrains Mono** — chosen for UI/mono typography. The unused Geist font and `next-themes` packages were removed during M1.
- **Theme tokens live in `src/index.css`** — user requested that `theme.css` be folded into the Tailwind entry instead of a separate `shared/styles/theme.css`.
- **Lowercase kebab-case filenames** — user requirement. React component identifiers remain PascalCase.
- **`LoadStage` is defined in `features/challenges/schema.ts`** — challenges are to the left of simulation in the dependency graph, and simulation may import challenges. This avoids a forbidden challenges → simulation import.
- **`cn` from the official `cn` package** — generated by current shadcn/Base UI registry; `src/shared/lib/utils.ts` re-exports it for project code.
- **Challenges include an optional `referenceSolution`** — needed for the gated sample solution and engine tuning, even though the §5.2 schema snippet omits it.
- **`referenceSolution`/`starterArchitecture` are optional** — authored challenges can ship without either, and both are validated by `architectureSchema` when present.
- **Route screens live in `features/<name>/pages/`** — user requirement. `src/routes` is removed; the router imports page components from feature public APIs. The not-found fallback stays in `app/pages/` because it is app-level, not a domain feature.
- **M1 placeholder behaviors for unmodeled kinds** — M1 had to keep every catalog kind runnable. Gateway and rate limiter enforced capacity; cache, database, queue, worker, CDN, DNS, and object storage stayed pass-through with representative latency until M2. Only DNS, gateway, rate limiter, and object storage remain pass-through.
- **M2 data components are deterministic approximations** — cache uses `(memory/workingSet)^0.6 * 0.98` with a 20s linear warm-up; CDN absorbs only static hits; DB read/write capacities share one equivalent queue; sharding uses a hot-shard multiplier; queue/worker backpressure uses the generic queue. These are teaching models, not benchmarks.
- **Storage exhaustion is checked per DB node** — the runner passes the IDs of databases whose `dataSizeGb` exceeds `shards * storagePerShardGb` into failure detection. This keeps the failure reason and root-cause node in the normal breach pipeline instead of special-casing a pre-run error.
- **Undersized cache wins root-cause attribution over the database symptom** — when a database is saturated and a cache's steady hit ratio is below 0.5, the cache is reported as the root cause. This makes the failure report actionable instead of blaming the component that merely absorbed the misses.
- **Diagnosis rules are data plus predicates** — `features/diagnosis/rules/catalog.ts` holds 16 ordered templates with metadata and `matches` functions. `diagnoseFailure` selects the first match and returns evidence; the M5 report modal can render it without duplicating rule logic.
- **Diagnosis is a separate feature, not part of simulation** — it imports architecture/challenges/simulation public APIs and follows the dependency direction. The engine stays focused on mechanics; explanation copy and rule prioritization can evolve independently.
- **Terminal nodes consume traffic** — a node with no outgoing edges is a sink, not a drop. This lets app servers and other terminal components pass a run instead of reporting unroutable traffic as errors.
- **Timeout is a failure reason** — `maxSimulatedSec` protects against non-terminal runs. The plan's four failure reasons remain, with `timeout` added as an engine safety outcome and documented in `ENGINE.md`.
- **Route pages are lazy-loaded** — every page route uses `React.lazy` behind an app-level `<Suspense>` fallback, and Vite splits React, React Router, Base UI, and icons into vendor chunks. This keeps the initial bundle smaller as the workspace grows.
- **oxlint covers correctness/performance; custom script covers architecture** — `.oxlintrc.json` enables React, react-perf, import, jsx-a11y, vitest, promise, and unicorn rules plus correctness/suspicious/perf categories. Rules oxlint cannot express (type aliases, import boundaries, engine purity) stay in `scripts/check-conventions.mjs`.
- **`next-themes` and `@fontsource-variable/geist` removed** — both were installed by the shadcn template but unused; theme state comes from the ScaleLab settings store.
- **React Flow is controlled by the design store** — the store owns nodes, edges, selection, and history. React Flow only renders derived flow nodes/edges and forwards position/remove/connect changes back to the store. This keeps one source of truth and makes undo/redo and validation straightforward.
- **Undo/redo uses architecture snapshots** — a `past`/`future` stack capped at 50 snapshots. Dragging is coalesced: the store records the architecture on drag start and commits it once on drag stop, so a full drag is one undo step.
- **Starter designs live with challenges** — `challenges/data/starter-designs.ts` owns the starter and reference graphs for all five challenges. The workspace loads one into the design store, and `starterArchitectureFor` returns a parsed clone so every visit starts clean.
- **Palette uses native drag-and-drop plus click-to-add** — the palette sets a custom MIME type and the canvas translates client coordinates with `screenToFlowPosition`. Clicking adds at the viewport center for pointer and keyboard users.
- **Inspector fields are generated from `COMPONENT_PARAM_SPECS`** — one spec table drives labels, ranges, units, select options, and hints. Every patch is validated with `componentParamsSchema` before reaching the store.
- **Designs autosave per challenge** — the workspace loads a saved design when one exists, otherwise the starter graph, and writes changes through the progress store after a 500 ms debounce. The debounce avoids a storage write for every node drag frame.
- **React Flow CSS is global and themed with `--xy-*` variables** — the graph needs to inherit ScaleLab theme tokens in all four palettes. React Flow is also split into its own lazy vendor chunk.
- **Simulation steps include edge rates** — `SimulationStep.edges` carries the routed rate per edge. The canvas and particle layer need flow thickness without re-running the engine or inspecting internal queue state.
- **Playback runs in a Web Worker with a main-thread fallback** — the worker advances 2 ticks every 50 ms at 1x and uses the same `driveTicks` helper as the fallback. This keeps the engine pure and keeps playback usable where workers are unavailable.
- **Run history samples at 4 Hz** — the run store receives every engine tick but appends a chart sample only every 0.5 simulated seconds, capped at 240 samples. Recharts stays responsive without rendering at 20 Hz.
- **Particles are one pooled canvas, not React nodes** — at most 400 particles are preallocated and reused. Density is sampled from edge rates, and the canvas reads the run store outside React so playback does not trigger a render per particle.
- **Challenge run configs live with challenges** — `loadProfile` and requirements are structural data owned by `features/challenges`. The workspace passes them to `startRun` without challenges importing simulation.
- **The workspace locks while running** — palette, inspector, drag/connect/drop, and design shortcuts are disabled during a run. This prevents the architecture from changing underneath a worker snapshot stream.
- **Footer credits the author** — `Built by Anirudh Kille` links to `https://anirudhkille.com`; it is a static external link, not application data.
- **Challenge data is authored Zod-validated constants** — `challenges/data/catalog.ts` builds five `Challenge` objects through `challengeSchema.parse`, injecting starter and reference architectures. The catalogue is compiled into the bundle; nothing is fetched.
- **Reference solutions are verified against the engine** — `simulation/__tests__/challenge-designs.test.ts` asserts every naive starter fails and every reference solution passes. This keeps the published numbers honest when engine constants change.
- **The sample solution stays gated** — the failure report unlocks it after three failed attempts, then requires a second confirmation before replacing the design. It is a teaching aid, not the default answer.
- **Hints reveal progressively** — the failure report shows one hint at a time, up to the challenge's three hints. The final hint names the technique but not an exact configuration.
- **Reports reuse the diagnosis feature** — the modal renders `diagnoseFailure` output instead of duplicating rule logic. It adds evidence, the p95 sparkline, hints, and actions around the existing explanation.
- **Scoring is deliberately simple** — one star for reaching target users, one for staying within budget, and one for 2× headroom. It rewards both correctness and efficiency without hiding the underlying SLO checks.
- **Attempts persist per challenge** — attempts are capped at 20 per challenge, grouped on the Progress page, and stored with their architecture snapshot for compare and restore.
- **Challenge and report dialogs are controlled** — the workspace owns open/closed state so it can prevent duplicate attempts and keep the editor locked while a report is visible.
- **Settings and progress use separate versioned keys** — settings stay under `scalelab:v1`; progress uses `scalelab:v1:progress`. Both are validated with Zod on hydration, and each corrupt slice gets its own timestamped backup instead of taking down the other.
- **Progress snapshots architecture, never simulation output** — attempts retain the design that produced them, but run steps, chart samples, and engine state are never persisted. This keeps the payload small and avoids stale simulation data.
- **Storage writes are best-effort** — the shared `safeLocalStorage` wrapper catches quota and blocked-storage errors, shows a rate-limited toast, and lets the session continue. It does not pretend the write succeeded.
- **Export is one validated envelope** — the export file contains an explicit format/version plus settings and progress. Import parses and Zod-validates the whole envelope before replacing anything, so a truncated or foreign JSON file cannot partially overwrite local data.
- **Restore is explicit** — comparing attempts never changes the design. Restoring loads the saved architecture, writes it as the challenge design, clears the run, and closes the report; the attempt history remains unchanged.
- **Streaks use local calendar days** — `summarizeProgress` groups attempt timestamps by local day and counts consecutive days ending today or yesterday. This matches what a learner sees on their own clock.
- **Onboarding completion is a settings field** — `onboardingComplete` is part of the versioned settings schema with a default of `false`, so older saved settings and exports hydrate without a migration. The tour is app-level chrome and can be replayed from the shortcuts dialog.
- **Keyboard help is a global dialog, not a route** — pressing `?` opens it unless focus is in an input, textarea, select, or content-editable element. The dialog lists workspace shortcuts and offers the tour replay action.
- **Accessibility is part of the shell** — the app shell starts with a skip link, `main` is programmatically focusable, dialogs have titles/descriptions, and icon-only controls carry accessible names. The onboarding and shortcuts flows use the same shared dialog primitives as the rest of the product.
- **Motion is opt-in at the utility level** — page fades use `motion-safe` utilities, while the global reduced-motion media query and the in-app preference disable transitions and edge-flow animation. No custom animation library was added for polish.
- **README screenshots are deferred** — there is no stable public deployment URL yet, so the launch README documents the interface and behavior without committing binary screenshots. Add them once the deployed build is fixed.
- **Architecture exposes a model-only subpath for the engine** — `@/features/architecture/model` re-exports schemas, types, catalog, graph, traffic, health, summary, editor, and param specs without React Flow components. Simulation engine files import this subpath so the Web Worker bundle cannot pull in browser-only UI code; `scripts/check-conventions.mjs` permits exactly that subpath and still rejects other deep feature imports.
